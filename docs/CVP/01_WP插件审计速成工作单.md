## 一、环境与目标选择

### 1.1 本地环境（半天搭好）

```
方案 A（推荐）：Docker 一键起
  docker run -d -p 8080:80 wordpress:latest
  浏览器 http://localhost:8080 完成 5 分钟安装向导
  后台 → 插件 → 安装目标插件 → 启用

方案 B：phpstudy/XAMPP + WordPress 官方 zip
```

### 1.2 目标筛选（决定产出效率的关键）

| 筛选条件 | 理由 |
|---------|------|
| 安装量 **1,000 ~ 100,000** | 太小：Patchstack 可能不收；太大：早被审烂 |
| 最近更新 **> 6 个月** | 维护差 = 洞多 |
| 版本 **0.x / 1.x 头几个版本** | 不成熟，防御代码缺失 |
| 类型优先：表单/上传/导入导出/统计/用户管理 | 用户输入面大 |
| 避开：已有大量 Patchstack advisory 的作者 | 人家有响应流程，轮不到你 |

插件源码拉取（不需要 WordPress.org 账号）：
```
https://downloads.wordpress.org/plugin/<slug>.<version>.zip
或 SVN 全历史：
svn co https://plugins.svn.wordpress.org/<slug>/tags/<版本>/
```

## 二、危险函数清单（按漏洞类型，附 grep 特征）

### 2.1 SQL 注入（Patchstack 收得多，CVSS 中高）

| Sink | 特征 |
|------|------|
| `$wpdb->query(...)` | 直接拼 `$_GET/$_POST` |
| `$wpdb->get_results / get_var / get_row / get_col` | 同上 |
| `$wpdb->prepare()` **误用** | 占位符缺失：`prepare("... $var ...")`——**变量在字符串里就是注入**，正确写法 `prepare("... %s", $var)` |

**常见误判**：`sanitize_text_field()` 不防 SQLi；`esc_sql()` 只防引号不防数字型注入；`absint()` 只有包住**整个**参数才有效。

### 2.2 XSS

| Sink | 特征 |
|------|------|
| `echo $_GET[...]` / `print $_POST[...]` | 直接回显 |
| `wp_send_json_success(['msg' => $_GET['x']])` | JSON 响应未转义（前端 innerHTML 就是 DOM XSS） |
| admin 页面回显用户参数 | Stored/Reflected 均可 |

### 2.3 越权 / IDOR（**新人最高产类型**，无需绕过任何防护）

| 特征 | 说明 |
|------|------|
| `add_action('wp_ajax_nopriv_xxx', ...)` | 未登录用户可调的处理函数——若该操作本应仅限登录/管理员 = 越权 |
| AJAX handler 缺 `current_user_can()` | 任何订阅者都能调管理员操作 |
| 缺 `check_ajax_referer()` | CSRF（常与越权叠加） |
| 增删改查只收 `id` 参数，不校验 `owner` | IDOR：改别人的记录 |

### 2.4 反序列化（罕见但致命，见到必捡）

| Sink | 特征 |
|------|------|
| `unserialize($_COOKIE[...]/$_GET[...])` | PHP 对象注入，配合插件内存在的魔术方法 POP 链 = RCE |
| `maybe_unserialize($user_input)` | 同上（注意 WP option 表存的是序列化值） |
| `file_exists('phar://...')` 等流操作 | 上传的文件名触发 phar 反序列化 |

### 2.5 SSRF

| Sink | 特征 |
|------|------|
| `wp_remote_get($_GET['url'])` / `wp_remote_post` | 服务端代抓任意 URL |
| `curl_init($_GET[...])` | 同上 |
| `file_get_contents($_GET['url'])` | 同上 + 借 `file://` 读本地文件 |

### 2.6 文件上传 / 任意文件读写

| Sink | 特征 |
|------|------|
| `move_uploaded_file` 无后缀白名单 | 上传 .php → RCE |
| `file_put_contents($_GET['path'], ...)` | 任意路径写 |
| `include/require $_GET[...]` | LFI/RCE |
| 导出功能 filename 未过滤 | 路径穿越 `../../` |

### 2.7 RCE（少见，遇到 = 大奖）

`eval` / `assert` / `system` / `exec` / `shell_exec` / `passthru` / `popen` / `call_user_func($_GET['f'], $_GET['a'])`

### 2.8 敏感信息

硬编码 API key、`define('DEBUG', true)` 上生产、导出接口无鉴权返回全部用户表。

## 三、五步审计流程（每插件 2-4 小时）

```
① 拉源码 → ② 跑 wp_audit.py（半自动扫） → ③ 人工追数据流
    → ④ 本地复现做 PoC → ⑤ 写报告提交
```

**数据流追踪要领**（与逆向算法追踪同构）：

```
入口点（Source）                     出口点（Sink）
─────────────────                  ─────────────────
$_GET / $_POST / $_REQUEST          $wpdb->*（SQLi）
$_COOKIE                            echo / json（XSS）
php://input                         include（LFI）
$_SERVER['HTTP_X_*'] 头             unserialize（POP）
上传文件 $_FILES['f']['name']       wp_remote_*（SSRF）
                                    unlink/fopen（文件）
中间问一句：source → sink 之间，有没有"真正有效"的过滤？
```

## 四、PoC 模板（报告必备五要素：插件/版本/类型/复现/影响）

### 4.1 SQL 盲注（时间型，最通用）

```http
GET /wp-admin/admin-ajax.php?action=plug_action&id=1 HTTP/1.1
Host: localhost:8080

（对照组）id=1                → 秒回
（实验组）id=1'+(SELECT+SLEEP(5))+'  → 延迟 5 秒 = 注入实锤
```

### 4.2 越权（nopriv + 无权限检查）

```http
POST /wp-admin/admin-ajax.php HTTP/1.1
Host: localhost:8080
Content-Type: application/x-www-form-urlencoded

action=plug_delete_record&record_id=8

未登录直接发 → HTTP 200 且返回 {"success":true}
→ 未授权删除任意记录（配合遍历 record_id = 全库删除）
```

### 4.3 反射 XSS

```http
GET /?page_id=3&plug_msg=<script>alert(document.domain)</script>
→ 响应体原样回显 = Reflected XSS
```

### 4.4 SSRF（云元数据）

```http
POST /wp-admin/admin-ajax.php
action=plug_proxy_fetch&url=http://169.254.169.254/latest/meta-data/
→ 返回云实例凭据 = 高危
```

### 4.5 报告信息结构（直接抄）

```
Plugin: <slug> (<精确版本号>)
Type: SQL Injection / Broken Access Control / ...
CVSS 3.1: 7.5 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N)  ← 用 first.org calculator 算
Steps: 1) 安装激活插件 2) 发送以下请求（原样 HTTP 报文） 3) 观察到…
Impact: 未授权用户可…（说清能拿到/改动什么）
Fix suggestion: 使用 $wpdb->prepare 占位符 / 添加 current_user_can 检查
Tested: WordPress 6.x, PHP 8.x, plugin <版本>
```

## 五、Patchstack 提交流程

1. **注册**：patchstack.com → Researcher 账号
2. **提交**：Dashboard → *Report a Vulnerability*（或 /database/report-vulnerability）
3. **填表**：插件 slug、受影响版本、类型、描述、PoC、修复建议（用 §4.5 结构）
4. **验证**：Patchstack 团队复现（数天~2 周），通过后邮件通知
5. **披露时间线**：他们联系插件作者 → 作者发修复版 → advisory 公开（**你的名字在 Credits**）→ CVE 编号分配（Patchstack 是 CNA）
6. **规则红线**：
   - 修复版发布前**绝不公开细节**（否则拉黑，CVE 也没了）
   - 同一插件多个洞 = 分开多份报告
   - 下架 ≠ 修复，等新版本号
7. **收益**：CVE credits（主要价值）+ bounty 计划（金额不大）+ 研究者排行榜
